# inventorybackend_test

Тестовое задание: серверная часть системы инвентаря и предметов на Node.js + TypeScript.
У игроков есть инвентарь, предметы можно выбрасывать на землю, подбирать и использовать; разные типы предметов ведут себя по-разному.
Полный текст задания — в папке [TaskDescription](TaskDescription/).

## Быстрый старт

Требования: **Node.js 22+** (проверено на Node 24). Внешних runtime-зависимостей нет, только `typescript` и `@types/node` для сборки.

```bash
npm install
```

```bash
npm test
```

```bash
npm start
```

- `npm test` очищает `dist/`, собирает проект (`tsc`) и запускает все тесты встроенным раннером `node:test`.
- `npm start` собирает проект и запускает сервер: игровой цикл с тиком раз в секунду. На каждом тике продвигаются эффекты онлайн-игроков и удаляются устаревшие предметы с земли, номер тика пишется в лог. Остановка — Ctrl+C. Ввода (CLI/HTTP) нет: логика проверяется тестами.

Запуск одного тестового файла после сборки:

```bash
node --test dist/core.test.js
```

## Архитектура

```
                main.ts — оркестратор (сборка приложения, подписка на тики)
                   │
      ┌────────────┼──────────────────────────┐
      ▼            ▼                          ▼
  GameLoop       Core — операции API        PlayerRegistry
  (тики)           │                          (онлайн-игроки → Player → активные эффекты)
                   ├── ItemTypeRegistry → ItemType (medkit, armor, ammo, bandage)
                   ├── InventoryFiller (раскладка по стакам)
                   ├── PromiseQueueWithKey (очередь операций по игроку)
                   └── IStorage → AsyncStorage (in-memory «БД» с задержкой)
```

| Модуль | Ответственность |
|---|---|
| `src/core.ts` | `Core` — операции API: `giveItem`, `dropItem`, `pickupItem`, `useItem`, `getInventory`, плюс `clearOldItems` для очистки земли. Ядро — набор операций, а не оркестратор: оно не решает, что происходит за тик. |
| `src/main.ts` | Оркестратор: создаёт зависимости, регистрирует типы предметов, на каждом тике продвигает эффекты игроков и вызывает очистку земли. |
| `src/items/` | `ItemType` — базовый класс типа предмета с обработчиками `onUse` / `onPickup` / `onDrop`; `ItemTypeRegistry` — реестр типов; конкретные типы `Medkit`, `Armor`, `Ammo`, `Bandage` и эффект `BandageEffect`. |
| `src/inventoryFiller.ts` | Чистая функция раскладки предметов по стакам (дозаполнение существующих, остаток в новые слоты). |
| `src/promiseQueue.ts`, `src/promiseQueueWithKey.ts` | Очередь асинхронных задач (следующая стартует после окончания предыдущей, упавшая задача очередь не ломает) и набор таких очередей по ключу с удалением опустевших. |
| `src/player.ts`, `src/playerRegistry.ts` | Игрок (позиция, `health`, `armor`, патроны, активные эффекты) и реестр онлайн-игроков. |
| `src/effectOverTime.ts` | Базовый класс эффекта во времени: счётчик оставшихся тиков и применение одного тика. |
| `src/IStorage.ts`, `src/IStorageWithFilters.ts`, `src/asyncStorage.ts` | Интерфейс хранилища и его in-memory реализация с настраиваемой случайной задержкой (имитация внешней БД). |
| `src/gameloop.ts`, `src/tickProvider.ts` | Игровой цикл на `setInterval` и абстрактный источник тиков с подпиской/отпиской. |
| `src/numberInRange.ts`, `src/pos.ts` | Число с гарантированным диапазоном; позиция и проверка «рядом». |
| `src/config.ts`, `src/result.ts` | Конфигурация (`pickupRadius`, `itemLifetimeTicks`) и тип результата операций `{ ok: true } \| { ok: false, reason }`. |

### API ядра

| Метод | Результат |
|---|---|
| `giveItem(playerId, typeId, amount = 1)` | `Promise<void>`; неизвестный тип или недопустимое количество — `RangeError` |
| `dropItem(playerId, itemId)` | `Promise<void>`; выбрасывается весь стак на позицию игрока |
| `pickupItem(playerId, groundItemId)` | `Promise<Result>`; «слишком далеко» и «уже подобран» — отказ в `Result` |
| `useItem(playerId, itemId)` | `Promise<Result>`; бессмысленное использование — отказ в `Result`, предмет не списывается |
| `getInventory(playerId)` | `Promise<IItemInstance[]>` |

### Как добавить новый тип предмета

Создать наследника `ItemType`, реализовать нужные обработчики (`onUse` возвращает `Result`), передать параметры через конструктор и зарегистрировать экземпляр в `ItemTypeRegistry` в `main.ts`. Ядро при этом не меняется.

## Известные ограничения

- **Нет общей атомарности между памятью и хранилищем:**
  - `useItem` сначала применяет эффект, потом записывает списание — при сбое записи эффект будет без списания;
  - `dropItem` сначала записывает инвентарь, потом кладёт предмет на землю; `pickupItem` сначала снимает предмет с земли, потом записывает инвентарь. При сбое второй записи предмет пропадёт — потеря выбрана вместо раздвоения, которое превращалось бы в эксплойт.
- Между истечением срока предмета и очисткой на ближайшем тике предмет ещё можно подобрать.
- Сбои (игрок, предмет или тип не найдены) бросаются обычным `Error`, своих классов ошибок пока нет.
- Хранилище in-memory: данные не переживают перезапуск процесса.
- Поиск предметов в радиусе — линейный проход, O(n).

## Принятые решения

Решения, принятые в ходе работы, и их обоснование.

### Сборка и запуск

- TypeScript компилируется `tsc` в `dist/`; перед сборкой `dist/` очищается (иначе в нём остаются скомпилированные копии перенесённых или удалённых файлов).
- Модули — ESM (`"type": "module"`, `module: nodenext`), поэтому в относительных импортах указывается расширение `.js`.
- Тесты — встроенный `node:test`, без внешних зависимостей. Тестовые файлы лежат рядом с кодом (`*.test.ts`).

### Время

- Время идёт тиками: `GameLoop` на `setInterval` со счётчиком тиков, интервал задаётся параметром. Цикл можно запустить и остановить из кода.
- Ядро (`Core`) — набор операций, а не оркестратор: оно не решает, что происходит за тик. Это решает оркестратор (`main.ts`): подписывается на тики игрового цикла и вызывает нужные операции.
- Источник тиков (`TickProvider`) — абстрактный класс с подпиской: `subscribe` возвращает функцию отписки. Ядро получает его, чтобы читать номер текущего тика; тесты подставляют свой источник, в котором тик выставляется вручную.
- Ошибка одного подписчика тика не роняет процесс и не мешает остальным подписчикам.

### Игрок

- Игрок: `id`, позиция `{ x, y }`, `health`, `armor`, патроны, активные эффекты.
- `health` и `armor` всегда в диапазоне 0..100, патроны — неотрицательные. Инвариант обеспечивает класс `NumberInRange`: значение зажимается в границы, `NaN` приводит к ошибке.
- Снаружи характеристики только читаются, менять их можно только методами игрока. Позиция отдаётся копией.
- Игроки — это «онлайн»-игроки: сервер стартует без игроков, они подключаются по ходу работы (id известен из авторизации, она вне рамок задания) и хранятся в памяти в `Map` по id.
- Инвентарь привязан к `playerId` и лежит в хранилище, поэтому переживает выход игрока: при повторном подключении с тем же id игрок получает свой инвентарь.
- Отдельной проверки «онлайн» нет: игрок онлайн, если он есть в реестре онлайн-игроков. `giveItem` и `getInventory` работают с инвентарём по `playerId`. Операции, которым нужен сам игрок (позиция, состояние) — `useItem`, `dropItem`, `pickupItem` — берут его из реестра; если игрока там нет, операция отклоняется.

### Предметы

- Реализованные типы: **medkit, armor, ammo, bandage** (bandage — эффект во времени).
- **Тип предмета** — класс-наследник абстрактного `ItemType`. Он хранит поведение (`onUse` / `onPickup` / `onDrop`, все необязательные — тип переопределяет только нужные) и параметры эффекта. На каждый тип — один экземпляр обработчика.
- **Реестр типов**: ядро знает только базовый класс и находит обработчик по id типа. Конкретные типы регистрируются снаружи, при сборке приложения. Поэтому новый тип добавляется без изменения ядра (без `switch` по типам).
- **Экземпляр предмета** — данные: id экземпляра, id типа, количество. В хранилище лежат только данные, без поведения.
- Правила типов (все величины задаются через конструктор и проверяются при создании типа):
  - **medkit** — восстанавливает здоровье до заданного максимума; если здоровье уже не ниже — отказ;
  - **armor** — поднимает броню на заданную величину; при максимальной броне — отказ;
  - **ammo** — добавляет заданное число патронов;
  - **bandage** — лечит по чуть-чуть заданное число тиков; при полном здоровье — отказ; пока действует предыдущий бинт — отказ.
- Тесты ядра используют тестовые типы, а поведение каждого реального типа проверяется в его собственных тестах — тесты ядра не растут с добавлением новых предметов.

### Эффекты во времени

- Длящиеся эффекты хранятся у игрока в списке **активных эффектов** (по ключу). Тип предмета состояния не хранит: `onUse` бинта только добавляет игроку эффект.
- Игрок не знает про игровой цикл: на каждом общем тике оркестратор продвигает эффекты всех онлайн-игроков через реестр. Отключившийся игрок выпадает из реестра и перестаёт получать тики сам собой.
- На тике игрока активные эффекты применяются к нему; закончившийся эффект удаляется из списка.
- Правило «нельзя, пока действует предыдущий» проверяется по списку активных эффектов, поэтому оно видно и типу предмета, и тестам.

### Стаки и инвентарь

- Стакаемость — свойство типа: тип задаёт максимальный размер стака. Нестакающийся предмет — тип с максимумом 1, отдельной логики для него нет.
- Инвентарь — список экземпляров без ограничения ёмкости (фиксированной сетки с пустыми слотами нет). Один экземпляр — один слот.
- `giveItem` и подбор сначала дозаполняют существующие стаки этого типа, остаток уходит в новые слоты. Стак, переполненный после уменьшения `maxStack` в конфиге, не уменьшается.

### Операции

- **drop** — выбрасывается весь стак. Предмет на земле: тип, количество, позиция и тик появления (`spawnTick`).
- **Исчезновение по таймауту:** ядро удаляет предметы, у которых `spawnTick < текущий тик − время жизни`. Предмет, появившийся на тике `S`, лежит на земле до тика `S + время жизни` включительно и удаляется на следующем. Очистку вызывает оркестратор на каждом тике, удаление — одной массовой операцией хранилища.
- **pickup** — только если игрок в радиусе `pickupRadius`. Подобранный стак раскладывается по стакам так же, как при выдаче: дозаполняет существующие, а новые слоты получают новые id. id в инвентаре и id на земле (`groundItemId`) независимы.
- **use** — количество уменьшается на 1, при 0 экземпляр удаляется из инвентаря.
- Бессмысленное использование запрещено: например, аптечку нельзя использовать при полном здоровье. Предмет при этом не тратится, а использование отклоняется.
- Обработчики `onDrop` / `onPickup` вызываются после успешной записи в хранилище.
- Порядок записей выбран так, чтобы при сбое предмет скорее пропал, чем раздвоился: `dropItem` записывает инвентарь, потом землю; `pickupItem` снимает предмет с земли, потом записывает инвентарь. `useItem` сначала применяет эффект, потом записывает списание (см. «Известные ограничения»).

### Хранилище и конкурентность

- Хранилище «тупое»: только сохраняет, читает и удаляет записи. Вся доменная логика (стаки, «рядом», эффекты) — в ядре. Так логика видна в коде, а хранилище легко заменить.
- Все операции хранилища асинхронные, со случайной задержкой в заданном диапазоне — имитация внешней БД. Наружу и внутрь передаются копии (`structuredClone`), как при передаче данных через сеть.
- Хранилище содержит два вида записей:
  - **инвентарь по `playerId`** — список слотов; читается и записывается целиком;
  - **предмет на земле** — id, тип, количество, позиция, `spawnTick`. Предметы на земле тоже находятся за асинхронным хранилищем, а не в синхронной памяти сервера, иначе гонка при подборе исчезла бы искусственно.
- Состояние игрока (`health`, `armor`, позиция, патроны, эффекты) живёт в памяти сервера, не в хранилище.
- Операции без отдельной проверки «существует ли» (чтобы не было гонки check-then-act):
  - инвентарь: прочитать по игроку, записать по игроку;
  - земля: добавить, прочитать по id, атомарно удалить с возвратом удалённого предмета, массово удалить;
  - запросы (`IStorageWithFilters`): предметы в радиусе, предметы старше заданного тика.
- Ядро зависит от интерфейса хранилища, а не от конкретной реализации.
- Атомарность отдельного вызова хранилища не делает атомарной операцию ядра: между `await` выполняется чужой код. **Подбор** защищён условной атомарной операцией «удалить, если существует, и вернуть удалённое»: решающим является её ответ, а не предварительное чтение. Кто первым удалил предмет с земли, тот его и получил, второй игрок получает отказ.
- **Изменения инвентаря одного игрока** защищает очередь по игроку (`PromiseQueueWithKey`): `giveItem`, `useItem`, `dropItem` и `pickupItem` целиком — от первого чтения до последней записи — выполняются в очереди своего `playerId`. Очередь отдельных вызовов хранилища не спасла бы от чередования «прочитал, прочитал, записал, записал». Операции разных игроков идут параллельно.
- Устройство очереди (`PromiseQueue`): задача передаётся функцией, а не промисом, чтобы очередь сама запустила её в свой черёд. Вызывающий получает промис результата своей задачи (вместе с её ошибкой), а хвостом очереди становится его «безопасная» копия, которая всегда завершается успешно, — поэтому упавшая задача не блокирует следующие. Когда после задачи никто не встал в очередь (хвост остался тем же), очередь сообщает об этом, и запись ключа удаляется, чтобы `Map` не росла бесконечно.
- Хранилище — приватная зависимость ядра. Тесты и CLI работают только через API ядра.

### Ошибки и результаты

- Недопустимые значения аргументов и конфигурации (границы, `NaN`, дробные количества, размер стака) — `RangeError`.
- **Отказ по правилам игры — не ошибка, а обычный результат операции** (`Result` с причиной): бессмысленное использование, «слишком далеко», «предмет уже подобран». Проигравший в конкурентном подборе получает именно отказ — это штатный исход.
- **Исключения — только для настоящих сбоев:** игрок, предмет или тип не найдены, недопустимые аргументы.
- Тип предмета сообщает ядру об отказе возвращаемым значением `onUse`, а не исключением.

### Запланированные улучшения

- **Пространственный индекс (сетка) для предметов на земле.** Делить мир на клетки размером с радиус и хранить предметы по ключу клетки: запрос проверяет только свою и соседние клетки вместо всех предметов.
- **Оптимистичная блокировка (версионирование) инвентаря в хранилище.** Чтение возвращает данные вместе с версией, запись принимает прочитанную версию и выполняется, только если та всё ещё текущая; иначе ядро перечитывает и повторяет операцию. Тогда гонку «прочитал, прочитал, записал, записал» ловит само хранилище, даже при обращении в обход очереди.
- **Разделение `onUse` на проверку и применение.** Тип отдельно отвечает «можно ли использовать» (без побочных эффектов) и отдельно «применить». Тогда `useItem` сможет проверить, записать списание и только потом применить эффект — ограничение «эффект без списания при сбое записи» исчезнет.
- **Свои классы ошибок** для сбоев (игрок, предмет, тип не найдены).
