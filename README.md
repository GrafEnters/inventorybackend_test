# inventorybackend_test

Тестовое задание: серверная часть системы предметов на Node.js + TypeScript — инвентарь игроков, выброс предметов на землю, подбор и использование.
Текст задания — в папке [TaskDescription](TaskDescription/).

## Запуск

Нужен **Node.js 22+** (проверено на 24). Runtime-зависимостей нет.

```bash
npm install
```

```bash
npm test
```

```bash
npm start
```

- `npm test` — сборка и все тесты (`node:test`).
- `npm start` — сборка и запуск игрового цикла (тик раз в секунду: эффекты игроков, очистка земли, лог тика). Ввода нет — логика проверяется тестами.

## Как проверить

| Сценарий | Тест |
|---|---|
| drop → pickup | `src/core.test.ts` — «Item transfer via ground between players» |
| Исчезновение по таймауту | `src/core.test.ts` — «Items disappear after its lifetime ends» |
| Эффект `use` | `src/core.test.ts` — «Usable item affect player», «Use unusable item doesn't waste it»; эффекты типов — `src/items/*.test.ts` |
| Конкурентный подбор | `src/core.test.ts` — «Concurrent pickup doesn't create copy of an item» |
| Параллельные операции одного игрока | `src/core.test.ts` — «Two identical useItem calls only one proceeds» |

Время в тестах не ждут: тест сам выставляет текущий тик.

## Архитектура

```
main.ts — оркестратор: собирает зависимости, на каждом тике вызывает нужные операции
 ├── GameLoop — тики (setInterval, подписка/отписка)
 ├── PlayerRegistry → Player — онлайн-игроки, их состояние и активные эффекты
 └── Core — операции API
      ├── ItemTypeRegistry → ItemType: Medkit, Armor, Ammo, Bandage
      ├── InventoryFiller — раскладка по стакам
      ├── PromiseQueueWithKey — очередь операций по игроку
      └── IStorage → AsyncStorage — in-memory «БД» с задержкой
```

API ядра (`src/core.ts`):

| Метод | Возвращает |
|---|---|
| `giveItem(playerId, typeId, amount = 1)` | `void` |
| `dropItem(playerId, itemId)` | `void` |
| `pickupItem(playerId, groundItemId)` | `Result` — успех или отказ с причиной |
| `useItem(playerId, itemId)` | `Result` — успех или отказ с причиной |
| `getInventory(playerId)` | `IItemInstance[]` |

Новый тип предмета — наследник `ItemType` с нужными обработчиками (`onUse` / `onPickup` / `onDrop`), зарегистрированный в `main.ts`. Ядро при этом не меняется.

## Ключевые решения

**Предметы**
- Тип предмета хранит поведение и параметры, экземпляр в инвентаре — только данные (id, тип, количество).
- Стакаемость задаёт тип через `maxStack`; нестакающийся предмет — это `maxStack = 1`. Выдача и подбор сначала дозаполняют существующие стаки.
- Бессмысленное использование (аптечка при полном здоровье, броня на максимуме, второй бинт поверх действующего) отклоняется, предмет не тратится.
- `drop` выбрасывает весь стак; подобрать предмет можно только в радиусе `pickupRadius`.

**Время и эффекты**
- Ядро — набор операций, а не оркестратор: что делать на тике, решает `main.ts`.
- Предмет на земле, появившийся на тике `S`, лежит до тика `S + itemLifetimeTicks` включительно.
- Длящиеся эффекты (bandage) хранятся у игрока как активные эффекты; на каждом тике оркестратор продвигает их у всех онлайн-игроков.

**Хранилище и конкурентность**
- Хранилище «тупое» (только чтение и запись записей, вся логика — в ядре), асинхронное, с задержкой и отдаёт копии данных — как настоящая БД. Предметы на земле тоже лежат в нём.
- Конкурентный подбор решает атомарная операция хранилища «удалить, если существует»: предмет получает тот, кто удалил его первым.
- Операции над инвентарём одного игрока выполняются строго по очереди (очередь промисов по `playerId`), операции разных игроков — параллельно.
- Порядок записей выбран так, чтобы при сбое предмет скорее пропал, чем раздвоился.

**Ошибки**
- Отказ по правилам игры — не исключение, а `Result` с причиной.
- Исключения — только для сбоев: недопустимые аргументы (`RangeError`), игрок, предмет или тип не найдены.

## Ограничения и что можно улучшить

- `useItem` сначала применяет эффект, потом записывает списание: при сбое записи эффект останется без списания. Улучшение — разделить `onUse` на проверку и применение.
- Предмет с истёкшим сроком можно подобрать до ближайшего тика очистки.
- Поиск предметов в радиусе — линейный. Улучшение — пространственная сетка.
- Защита инвентаря держится на очереди в ядре. Улучшение — версионирование записей в хранилище (оптимистичная блокировка).
- Для сбоев используется обычный `Error`, своих классов ошибок нет.
- Хранилище in-memory: данные не переживают перезапуск.
