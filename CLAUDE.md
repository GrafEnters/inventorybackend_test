# CLAUDE.md

## Что это за проект

Тестовое задание на позицию JS/TS/Node.js-разработчика: серверная часть системы инвентаря и предметов.
Полный текст — `TaskDescription/Тестовое задание_ инвентарь и предметы.html`.

Кратко:

- Стек: Node.js + TypeScript.
- Игрок: `id` + позиция `{ x, y }`, характеристики `health`, `armor` (0..100), при необходимости патроны/пометки.
- «Рядом» — расстояние не больше настраиваемого радиуса. Время идёт шагами `tick`.
- Хранилище асинхронное (Promise), как будто за ним внешняя БД.
- Ядро — единый источник правды для инвентарей и предметов на земле.
  Выброшенный предмет лежит на позиции игрока, его может подобрать любой игрок рядом, через настраиваемое время он исчезает.
- Новый тип предмета добавляется без изменения ядра. Типы описывают поведение обработчиками `onPickup` / `onDrop` / `onUse`.
- API: `giveItem(playerId, itemType, amount?)`, `dropItem(playerId, itemId)`, `pickupItem(playerId, groundItemId)`,
  `useItem(playerId, itemId)`, `getInventory(playerId): IItemInstance[]`.
- Реализовать 4 типа из: medkit, armor, bandage (эффект во времени), ammo, flare (подсветка игроков рядом на N тиков), repairkit.
- ООП, ядро отделено от ввода (тесты/CLI) и от хранения, без глобальных переменных, все значения конфигурируемые.
- Обязательно показать: drop → pickup, исчезновение по таймауту, эффект use, конкурентный подбор одного предмета двумя игроками.
- README: запуск, тесты, обзор архитектуры.

## Главное ограничение: код пишет только пользователь

HR попросил не использовать ИИ для написания кода; советоваться можно. Поэтому действуют жёсткие правила.

### 1. Claude не меняет файлы — вообще

- Весь код, 100% каждого символа, пишет пользователь. Это касается и кода, и конфигов (`package.json`, `tsconfig.json`, тестов, README и т.д.).
- Запрещено: Write, Edit, NotebookEdit, любые shell-команды, которые создают/меняют/удаляют файлы
  (`sed -i`, перенаправление `>`, `npm install`, `npm init`, `tsc` с выводом в файлы, форматтеры с записью, `git commit`, `git checkout`, создание веток и т.п.).
- Разрешено: читать файлы (Read, Grep, Glob, `cat`, `git status/diff/log`) и, если пользователь попросит,
  запускать команды, которые ничего не пишут на диск (например, тесты или `tsc --noEmit`), чтобы посмотреть вывод.
- Если пользователь сам попросит что-то изменить — напомнить про это правило и предложить сделать это ему.
  (Единственное исключение было при создании проекта: этот CLAUDE.md и раздел про ИИ в README написаны по прямой просьбе.)

### 2. Инструменты пользователя

Пользователь работает в WebStorm: обычный автокомплит и подсветка синтаксиса IDE — это нормально.
Никакой генерации кода ИИ (ни Claude, ни AI-ассистентов IDE).

### 3. Совместно: архитектура и планирование

Обсуждаем вместе и это можно делать развёрнуто:

- архитектуру, слои, границы модулей, ответственности классов;
- глобальные решения (структура хранения, модель времени/тиков, как обеспечить атомарность подбора, как регистрировать типы предметов, конфиг, способ тестирования);
- план работ: что пользователь кодит, в каком порядке.

Допустимо: описывать решения словами, схемами, перечислять сущности и их обязанности, обсуждать плюсы и минусы вариантов.
Недопустимо: выдавать готовые интерфейсы/классы/сигнатуры, которые можно скопировать в проект как есть.

### 4. Вопросы по синтаксису и «как сделать X»

- Объяснять синтаксис, семантику, поведение языка/рантайма, стандартной библиотеки, инструментов (TS, Node.js, тест-раннер, npm).
- Примеры кода — только минимальные (несколько строк), на абстрактных сущностях, не из предметной области задания
  (не `Player`, `Inventory`, `Item`, `pickupItem` и т.п.), иллюстрирующие именно синтаксис/конструкцию.
- Запрещено давать готовые методы, классы, функции или крупные куски кода для проекта, а также «почти готовый» код, который останется лишь переименовать.
- На «как мне сделать X» — объяснять подход и нужные инструменты языка словами; реализацию пишет пользователь.

### 5. Ревью

Когда пользователь просит отревьюить написанный кусок:

- Читать актуальные файлы (и `git diff`, если уместно).
- Указывать проблемы текстом: где (`файл:строка`), что не так и почему это проблема — какой сценарий сломается, какое требование задания нарушено, чем это плохо.
- **Не говорить, как исправить.** Не предлагать код, не подсказывать конкретное решение. Пользователь придумывает исправление сам.
- Можно указывать категорию и серьёзность (баг, гонка, типизация, нарушение требования, читаемость, архитектура).
- Если пользователь явно попросит подсказку — дать направление на уровне идеи/концепции, без кода.
- Итерации: пишет → ревью → исправляет → снова ревью, пока решение не будет отполировано.

## Порядок работы

1. Разобрать задание, обсудить архитектуру и ключевые решения.
2. Составить план реализации по шагам.
3. Пользователь пишет код шаг за шагом, по ходу задаёт вопросы (правило 4).
4. После каждого куска — ревью (правило 5), багфикс силами пользователя.
5. Тесты/сценарии проверки из раздела «Как проверить» задания.
6. README: запуск, тесты, обзор архитектуры (пишет пользователь).
